# Policy in Action Library：对话上下文与跨会话记忆设计

编写日期：2026-10-22。

代码基线：本地 `feature/durable-document-tasks`，HEAD `2a45d2a`。本文区分“当前代码行为”“静态代码推导出的风险”和“建议新增的能力”。未修改运行时代码，未调用付费模型，未将设计参数当作实测结果。

## 1. 结论与需求边界

当前系统有两条不同的上下文路径：

- Direct：读取最近 10 条聊天消息，按原文传给回答模型；没有历史摘要。
- ReAct：通过 PostgreSQL Checkpointer 累积会话状态；调用模型时过滤旧轮次的工具调用消息，但保留旧轮次的用户消息和普通助手消息；没有历史摘要，也没有对这些自然语言历史设置统一 Token 上限。

因此，当前系统既不是所有模式都“无限塞 history”，也不是已经实现了压缩式记忆。Direct 是固定消息数量窗口，ReAct 是过滤工具轨迹后的持续累积历史。

建议升级为：

> 原始聊天记录作为可追溯底稿；当前对话使用“结构化摘要 + 最近原文 + 当前任务状态”；跨会话使用“按研究主题组织的可检索片段”；所有模型请求经过统一 ContextBuilder，受 Token 预算、文档范围和引用规则约束。

用户提出的“聊天结束后做 Embedding，未来相关时检索回来”可以保留为方向，但应调整三个地方：不只等待聊天结束；不只给整段聊天生成一个向量；命中后不直接把整段历史全部塞回模型。

### 1.1 将“跨文档对话”拆成三个独立需求

| 需求 | 示例 | 当前状态 | 建议 |
|---|---|---|---|
| 同一轮比较多份文档 | “比较这三份政策的资金来源” | 请求和检索范围已经支持多个 document_ids | 增加分问题检索和文档覆盖检查 |
| 同一聊天连续研究、切换或追加文档 | “把刚才的维度应用到新上传的文件” | 能保留历史并传入新文档集合，但缺少统一指代解析和结构化研究状态 | 增加研究状态、文档角色、范围版本 |
| 新聊天延续旧聊天 | “沿用上次住房政策研究的比较框架” | 未实现跨会话语义召回 | 增加可检索研究片段和记忆读取工具 |

本方案默认同时解决这三种需求。优先保证当前聊天正确，再引入跨会话召回。

### 1.2 第一版产品行为

1. 用户可以连续追问，系统理解“它”“上一份”“刚才的第二项”等指代。
2. 用户可以在同一研究中追加文档，已有比较维度和待办不会丢失。
3. 用户开启历史关联后，相关旧聊天可以自动成为候选，无须输入固定口令。
4. 记忆被实际使用时，界面展示来源聊天、时间和可打开的消息范围。
5. 用户可以关闭历史关联、排除某个聊天或手动指定一个旧聊天。
6. Document Analysis 的政策事实仍必须有当前允许使用的原文依据。历史聊天只能帮助理解意图、恢复研究进度和定位来源。

## 2. 当前代码怎样管理上下文

### 2.1 聊天展示记录与运行状态是两套存储

`chat_sessions / chat_messages` 保存用户可见的会话、消息、引用和状态。读取某个聊天详情时，可以返回完整消息列表。

ReAct 另有 PostgreSQL Checkpointer，保存 LangGraph 状态、消息和工具执行进度。`thread_id` 直接使用 `session_id`。这套状态服务于继续运行和 interrupt/resume，不等于已经有跨聊天记忆。

“数据库里存了全部记录”和“每次请求都把全部记录发给模型”是两个不同问题。

### 2.2 Direct：最近 10 条消息的原文窗口

`ChatTurnService.start()` 先验证会话属于当前用户，再读取旧历史，然后插入本轮问题。这避免了当前问题在 history 中重复出现。

`MAX_HISTORY_TURNS = 5`，但实际 SQL 是：

```sql
SELECT role, content
FROM chat_messages
WHERE session_id = %s
ORDER BY created_at DESC
LIMIT max_turns * 2;
```

随后逆序，恢复时间顺序。

这里严格来说是“最近 10 条消息”，并不是严格按完整问答对选取 5 轮：没有在这个查询中配对轮次，也没有过滤失败、未完成状态。正常的一问一答情况下才近似等于 5 轮。

生成模型大致接收：

```text
System：角色要求 + 本轮检索出的文档片段 + 本轮引用说明
User：历史问题 1 原文
Assistant：历史回答 1 原文
……最近约 5 轮……
User：当前问题 + 风格要求
```

没有对旧历史执行总结、重要性抽取、语义筛选或按 Token 自动裁剪。

旧回答通常会带着原有 `[1]` 等文本进入 history；旧回答的结构化 citations 信息并没有通过 `get_history_for_llm()` 一起传入。历史回答里的引用编号，不能直接视为本轮编号。

### 2.3 Direct 的检索并未先理解完整对话

`run_retrieval()` 接收 history，但构造 `RetrievalRequest` 时使用的是当前 `question`。历史被保存在状态里，主要供后续生成使用。

因此可能出现：回答模型知道“它”指谁，但检索模型或检索器只看到“它的资金来源呢？”，没有得到完整的检索问题。

这意味着仅增加历史长度未必能解决连续追问。应在文档检索之前先补全当前问题，并明确检索对象。

### 2.4 ReAct：Checkpoint 累积消息，模型输入过滤旧工具轨迹

第一次进入尚无 checkpoint 的 ReAct 会话时，路由用数据库中的最近历史初始化 messages。之后只追加当前问题，不重复导入数据库历史。

`AgentState.messages` 使用 `add_messages` reducer。Checkpoint 保留会话中的消息，包括工具调用和结果。

每次 Agent 决策以及最终回答之前，`_messages_for_current_turn()` 会：

1. 找到最新一条 HumanMessage。
2. 对它之前的历史，保留用户消息和有正文、没有 tool_calls 的助手消息。
3. 删除这些旧轮次的 AI 工具调用消息和 ToolMessage，避免旧预算耗尽等观察污染新问题。
4. 对当前用户问题之后的消息，保留本轮工具调用过程。

近似输入：

```text
System：本轮 Agent 规则
历史用户消息 + 历史普通助手消息，持续累积
当前用户问题
当前轮 Agent 工具调用和工具结果
```

这是一种按消息类型过滤的设计，不是语义压缩或总结。首次初始化受数据库 10 条消息窗口影响；形成 checkpoint 后，新发生的 ReAct 对话可以继续累积，不能把它理解成始终只有 5 轮。

ReAct 的检索工具参数 `query` 由模型生成，因此模型可能利用历史改写问题；但这是模型在工具决策中的行为，不是两条模式共享的、经过验证的 Query Understanding 阶段。

### 2.5 已有少量结构化的会话记忆

`web_pages_seen` 会保存本聊天曾搜索到的网页，按 URL 去重，最多 50 条。网页入库工具利用它解析“上一轮第二个网页”，避免模型凭记忆重写 URL。

这是一个有价值的现有设计：重要对象通过稳定标识和结构化字段保存，再由工具解析。可以把同样的思路扩展到政策文档、比较维度、研究任务和历史证据定位。

它只在同一 session/thread 内有效，不会自动带到新聊天。

### 2.6 当前限制的是局部材料，并非整个请求的 Token

检索格式化函数按 `max_context_characters` 限制文档 context，代码默认值为 200,000 字符，运行环境可覆盖。

这个上限：

- 以字符计数，不是模型 Token。
- 主要作用于格式化的检索 context。
- 没有将系统提示词、历史、工具定义、当前工具结果和输出预留统一纳入预算。
- ReAct 的文档工具会把结果片段放进 ToolMessage，不能假定它们全部经过 Direct context 的同一上限。

因此，应增加覆盖每次模型调用的预算器，而不是只调整这个字符参数。

### 2.7 从当前代码可推导出的切换风险

Direct 主要读取 `chat_messages`；已有 ReAct thread 主要读取 checkpoint messages，并仅追加最新问题。如果同一聊天先运行 ReAct，中间运行几轮 Direct，再回到已有 ReAct thread，路由没有显示地把中间新增的 Direct 消息同步进该 checkpoint。

这意味着上下文可能随模式切换而不一致。这是静态代码推导，本文未运行切换场景测试。建议通过统一的消息序号和上下文读取入口消除两套历史来源的分歧。

## 3. 设计原则：持久记录、模型上下文、记忆索引分别负责什么

建议保留三层职责：

| 层 | 保存内容 | 主要用途 | 是否每次全部发给模型 |
|---|---|---|---|
| 原始记录层 | 完整用户/助手消息、引用、状态；必要的工具轨迹 | 展示、审计、重新生成摘要、定位原话 | 否 |
| 当前研究上下文 | 活跃任务、结构化摘要、最近消息、当前来源集合 | 理解本轮问题、持续研究 | 按预算选择 |
| 跨会话记忆索引 | 研究主题摘要、讨论片段、消息范围、来源定位、Embedding | 在需要时发现相关历史 | 只发送少量命中内容 |

向量是检索索引。真正被模型阅读的仍是文本、结构化信息及必要原始消息。

LangGraph 官方把单个 thread 的持久状态和跨 thread 的长期记忆区分处理；后者可以用带 namespace 的 Store。项目可以采用这个抽象，也可以用现有 PostgreSQL/pgvector 自行实现 MemoryService，不必因为引入记忆就更换存储基础设施。参考：[LangChain 长期记忆](https://docs.langchain.com/oss/python/langchain/long-term-memory)。

## 4. 同一聊天：结构化摘要、近期原文与研究状态

### 4.1 不只总结“聊过什么”

摘要应服务于下一轮行动，建议包含以下字段：

```json
{
  "research_goal": "比较两个地区的社会住房资金机制",
  "comparison_dimensions": ["资金来源", "申请主体", "监督机制"],
  "constraints": ["只采用所选政策原文", "用中文输出"],
  "document_roles": [
    {"document_id": "doc-a", "role": "比较对象 A"},
    {"document_id": "doc-b", "role": "比较对象 B"}
  ],
  "confirmed_user_decisions": [
    {"text": "比较范围仅含政府补贴", "message_id": "message-12"}
  ],
  "prior_findings": [
    {
      "text": "先前回答提出了一个资金机制差异",
      "claim_origin": "assistant",
      "evidence_refs": ["evidence-ref-a"],
      "verification_required": true
    }
  ],
  "open_questions": ["文档 B 是否规定私人资本参与条件"],
  "covered_through_sequence": 18,
  "summary_version": 3
}
```

这些值仅是结构示例，不代表数据库中确有这些文档或政策条款。

重点是区分用户明确说过的话、用户做出的决定、助手推断和原文支持的发现。不能把助手的历史回答直接升级成已确认的政策事实。

“用户随后问了下一题”也不能视为用户认可了上一条助手结论。

### 4.2 摘要与原始消息的覆盖边界

为每条消息增加稳定的会话内顺序或等价的可靠游标。摘要记录覆盖到哪个完整轮次；最近原文从摘要游标之后读取。

```text
原始消息：1 … 18 | 19 … 24 | 25 当前问题
摘要覆盖：1 … 18
近期原文：19 … 24
当前输入：25
```

这样既不会把同一批信息以摘要和全文重复注入，也不会因为摘要尚未完成而漏掉新消息。

第一版可在历史达到配置的 Token 阈值时生成摘要，保留最近若干完整轮次原文。轮次数是辅助条件，实际边界由 Token 和语义完整性决定。

摘要不必每轮全量重算。可以使用旧摘要和新增完整轮次进行增量更新，但要保留版本与来源消息；发现漂移或任务大幅变化时，从相应原始片段重建，不应无限递归地“摘要的摘要”。

LangGraph 官方提供 Token 裁剪、摘要和自定义消息筛选的实现方向；本项目适合保留现有 StateGraph，添加自己的摘要与输入投影，不需要整体替换 Agent 框架。参考：[LangGraph 记忆管理](https://docs.langchain.com/oss/python/langgraph/add-memory)。

### 4.3 持久状态与发给模型的上下文分开

第一阶段先不破坏现有 checkpoint：保留可恢复状态，在调用模型前由 ContextBuilder 生成一份精简输入视图。

对 ReAct：

- 旧完整轮次：通过摘要和近期对话提供必要信息。
- 当前工具调用链：保留合法的调用与结果配对。
- 长工具结果：执行工具时就控制返回量，必要时用结果句柄和细读工具获取局部材料。
- interrupt/resume：使用暂停时的研究状态、来源范围和摘要版本；不要在等待用户回复期间重写进行中的工具链。

如果未来要压缩 checkpoint 本身，应单独设计保留与归档策略。裁剪模型输入和删除持久状态不是同一个操作。

多数模型提供方要求工具调用有对应结果，因此不能为了节省 Token 只删除 ToolMessage 或只留下 tool_calls。参考：[LangChain 消息删除约束](https://docs.langchain.com/oss/python/langchain/short-term-memory)。

### 4.4 同一聊天避免并发写乱序

同一 session 同时发起两条新问题时，应排队或通过版本检查拒绝冲突，防止摘要游标、来源范围和 checkpoint 交叉覆盖。

每轮建立不可变的 ContextSnapshot：使用哪个摘要版本、哪些近期消息、哪些文档版本、哪些历史片段。异步摘要更新只影响后续新轮次；resume 使用原快照和必要的当前权限复核。

## 5. 跨会话记忆：怎样改进“每个 Chat 一个 Embedding”

### 5.1 整个 Chat 一个向量的局限

1. 一个聊天可能有很多主题，单个向量难以定位其中的小问题。
2. 聊天很长时，需要截断或摘要；只索引摘要又可能遗漏具体决定、表格维度或原话。
3. 命中了聊天，并不等于该聊天的所有内容都与当前问题相关。
4. 整段展开会重新带回无关内容、已被纠正的回答和旧文档范围。
5. “结束聊天”没有稳定事件：用户可能直接关闭窗口，或几周后继续同一聊天。

整聊天摘要向量可作为粗粒度入口，但不应成为唯一索引。

### 5.2 推荐记忆粒度

**聊天级摘要**：概括整个研究的主题、主要对象、最近进度，适合发现“之前在哪个聊天讨论过”。

**研究片段，也称 episode**：一个相对完整的任务或子主题，例如“确定比较维度”“讨论资金来源”“修改输出结构”。每个片段有独立向量、结构化摘要和原始消息范围。

**长期偏好**：语言、输出格式等。如果确有产品需求可以单独维护。第一版不必建立复杂用户画像，尤其不能把一次临时要求当成永久偏好。

episode 的边界可结合话题切换、任务完成和长度上限。初期可以先用若干完整轮次窗口加小幅重叠，后续再按评测改成语义分段；不需要为第一版再开发复杂的话题识别 Agent。

### 5.3 一个记忆片段至少携带什么

```text
身份：memory_id、user_id；未来有研究空间时再加入 workspace_id
定位：session_id、message_start/end、创建时间、覆盖游标
检索文本：主题、用户问题、重要实体、简短摘要
研究状态：目标、维度、明确决定、未完成事项
来源：document_id、文档版本、页码、quote/定位信息、原始 citation
状态：有效、被后续修订、来源不可用、索引版本
向量：embedding 与 embedding_model_version
```

Embedding 主要作用于“主题 + 用户问题 + 重要实体 + 摘要”等检索文本。不要把所有字段随意拼接，更不要只保存向量后丢弃可读文本和原始定位。

最小实现可只保存聊天级摘要与 episode，不必为每条消息都建向量。

### 5.4 何时更新索引

以“完整轮次成功落库”为可靠事件，合并短时间内的更新，再异步更新摘要和相关片段。关闭窗口或归档聊天可以触发补充刷新，但不能成为唯一触发点。

建议流程：

```text
助手回答成功落库
→ 同一事务记录待处理的记忆任务/事件
→ 后台 worker 合并更新
→ 生成或更新摘要、episode
→ Embedding
→ 原子发布新的可检索版本与覆盖游标
```

不要把暂停中的澄清、空的 streaming 消息和失败半答当成完整研究成果写入记忆。需要保留用户尚未解决的问题时，应显式标记为 unresolved。

项目已有 PostgreSQL 持久任务的工程模式，可以复用其任务认领、重试和幂等思想；不应直接把聊天任务伪装成文档入库任务。根据现有表约束，新增独立 memory task 或通用 outbox 更清晰。暂时不需要引入新的向量数据库、Redis 或一套额外 Agent 平台。

任务键可包含 session_id、覆盖游标和索引版本，保证重试不产生重复片段。新版本写完后再切换可见指针，避免搜到半成品。

对于“刚在另一个聊天讨论过、索引还没刷新”的情况：用户明确指定聊天时直接读取授权的原始记录；自动召回可增加最近更新聊天的轻量回查。不要把索引未更新解释成用户从未讨论过。

### 5.5 检索回来后读多少

推荐流程：

```text
当前问题与研究状态
→ 权限与产品范围过滤
→ episode 向量召回 + 关键词/实体召回
→ 去重、相关性重排、必要的时间约束
→ 选取少量片段
→ 按 message_id 回查原文与上下文
→ 再决定哪些内容进入本轮上下文
```

聊天级摘要可以与 episode 并行召回后合并，不要强制“先命中聊天摘要，才允许搜该聊天片段”。否则摘要没有写到的小话题会在第一阶段被挡掉。

第一版可用 pgvector 做片段召回，再加入已有关键词检索的思路。聊天记忆应有独立语料和权限条件，不能直接混进政策文档索引。可以复用检索算法、Embedding 客户端和 reranker 能力，但结果类型和评分阈值要单独评测。

初始候选数可取十几到几十条，重排后只给模型少数片段；具体数值依据数据规模和评测调整。时间应作为过滤条件或有限加权，“最新”不能自动压过用户明确要求的旧讨论。

向量相似度不是“这条记忆可用的概率”。不能直接照搬文档检索阈值，更不宜用未校准的 0.8 一类常数作为可靠性保证。

## 6. 如何自动触发历史检索

### 6.1 不要求固定关键词或正则口令

正则适合识别某些明确命令，例如用户关闭记忆。但它很难完整覆盖：

- “沿用我上周那个框架。”
- “这次还是按之前的维度。”
- “把新文件补到原来那个比较里。”
- “之前聊的两个州，哪个对私人资本更开放？”

也可能误触发：“这份历史记录保留政策写了什么？”中的“历史记录”指文档内容。

检索触发应主要依赖语义、当前任务状态和明确的产品开关。

### 6.2 推荐：确定性边界 + 结构化语义路由 + 工具补查

先处理确定性规则：

1. 用户关闭历史关联：不跨会话召回。
2. 用户指定某个聊天：直接在该聊天范围读取，不必先用向量猜它是哪一个。
3. 当前聊天最近消息与摘要足以解析：优先本地上下文。
4. 新聊天、上下文缺口、延续旧任务等情况：交给语义路由判断是否跨会话检索。

增加 QueryUnderstanding 步骤，把指代消解、问题补全、任务分类和历史检索意图合并到一份结构化输出中，避免为每个小判断都增加模型调用。

```json
{
  "intent": "document_compare",
  "standalone_query": "按此前确定的资金来源、申请主体、监督机制比较当前两份文档",
  "unresolved_references": ["此前确定的比较维度"],
  "memory_action": "search",
  "memory_query": "用户此前住房政策研究确定的比较维度",
  "time_constraint": null,
  "requested_document_references": [],
  "reason": "当前聊天没有这些维度，用户明确延续先前研究"
}
```

这里的 reason 是简短可审计说明，无需保存模型内部思维过程。由服务端校验输出和权限；模型提出的文档标识必须经过实体解析，不能自行生成合法来源范围。

如果无法可靠消解指代，输出 unresolved，而不是为了补全问题编造地区、年份、政策名称。

### 6.3 根据问题类型选择动作

| 用户问题 | 默认动作 |
|---|---|
| “这份文档规定的申请条件是什么？” | 检索所选文档，通常不需要历史召回 |
| “那它的资金来源呢？” | 先用当前摘要和近期消息消解“它”，不足时澄清 |
| “沿用之前住房研究的比较维度” | 搜索历史研究片段，读取确定维度的原始消息 |
| “看看我上次到底选了哪些维度” | 回答聊天历史事实，附聊天来源 |
| “比较上次那份政策与这次新文件” | 先找旧聊天和文档身份，再确认/解析本轮有效文档范围，回查双方原文 |
| “分析这份历史记录管理办法” | 这是文档分析，不因“历史记录”字样触发聊天记忆 |
| “这次只看这两份文件，别参考以前的聊天” | 显式关闭跨会话召回 |
| 两个旧研究均高度相关且要求不同 | 展示候选或问一个具体澄清问题，不能混合两套决定 |

同一聊天中“它”没有明确指向时，不应立即遍搜所有聊天。全局召回容易把本来局部的歧义变成更大歧义。

### 6.4 ReAct 增加什么工具

建议提供：

```text
search_chat_memory(query, optional_time_range, optional_session_hint)
read_chat_excerpt(memory_id 或 session_id + message_range)
```

user_id、可访问范围和 Token 上限由服务端注入，不能由模型自由填写。搜索返回简短候选；读取返回被授权的局部原文、结构化信息和来源，不允许无界读取整个账户历史。

初始预算可限制每轮 1 次搜索、1 次局部读取；用户明确要求深入回顾时再适当放宽。无结果时可以澄清或继续当前任务，不应一直换词搜索。

Direct 也调用同一 MemoryService 和 ContextBuilder，由编排层执行搜索。否则只在 ReAct 中加入工具，会让同一问题因模式切换而拥有不同记忆能力。

### 6.5 工具触发需要适配当前 ReAct 协议

当前 Document Analysis 在一次 `search_internal_documents` 后，会把可用工具限制为 `prepare_final_answer`。因此新增一个工具函数并不代表流程一定能调用它。

建议把多数历史解析放在文档检索之前；确需中途补查时，显式修改允许的状态转移、调用预算和不足证据路由。记忆读取不是一个政策证据 tier，不应写入 `evidence_sources = internal` 来绕过原文检索。

已有 `prepare_final_answer` 和“证据不足则拒答”的约束可以继续保留，只需让它们理解回答对象的不同：

- `policy_answer`：必须满足文档证据要求。
- `conversation_recall`：回答用户过去说过什么，可依据原始聊天消息；显示聊天出处。
- `mixed`：先恢复研究状态，再对政策结论进行文档检索。

这避免出现“查用户当时选了哪些维度，也被要求必须找到 PDF 证据”的错误，同时不会把历史回答包装成政策证据。

## 7. 跨文档研究需要的额外设计

### 7.1 让研究对象和本轮文档范围成为结构化状态

建议为当前研究保存：研究目标、比较维度、文档角色、文档集合版本、已完成问题和未完成问题。

来源范围采用确定规则：本轮显式选择优先；用户明确要求延用时才继承；区分“未传来源”“明确清空来源”。Document Analysis 没有有效文档时引导选择，不能默默把历史提到的所有文档加入范围。

文档切换可以保留研究方法和比较维度，但旧文档中的事实不能自动成为新文档的事实。

### 7.2 比较问题按对象与维度检索

只对所有文档做一个全局 Top-K，候选可能被一份更长或更相似的文档占满。建议先形成覆盖计划，例如：

```text
文档 A × 资金来源、申请主体
文档 B × 资金来源、申请主体
```

对目标对象分别召回，再合并、去重和重排。Coverage Check 输出“哪些对象的哪些维度有证据，哪些没有”。

这不是要求每个文档机械平均分配 Token：优先保证问题所需的比较双方都有机会进入候选。没找到某条款，应表达“本轮检索未找到依据”，不能直接断言政策不存在该条款。

当前 Analysis 的一次文档搜索协议可以保留外层单次调用，在检索服务内部执行多个子查询；这样不必让 Agent 为每个维度无约束循环。

### 7.3 稳定证据引用，避免跨轮编号混淆

内部证据身份应使用 document_id、文档版本与稳定定位；chunk_id 可以作为当前索引定位，但不应是唯一长期身份。重切块后可用页码、原文 quote 和内容哈希辅助重新定位。

前端 `[1]` 只是当前回答的显示编号。历史摘要不应只保留 `[1]`，而应保存稳定 evidence_ref，再在本轮重新映射显示编号。

Document Analysis 的引用规则：

1. 旧聊天帮助确定要查哪份政策、哪一页、哪项研究决定。
2. 服务端复核文档存在、版本和当前权限。
3. 在当前允许的范围回取原文或重新检索。
4. 本轮证据检查通过后，才进入本轮引用集。

如果旧文档未在当前允许的范围内，界面可提供“将该文档加入比较”的明确操作。不能在后台无提示地扩展用户当前选择的政策材料。

文档版本已变时，应区分“当时研究的旧版本”和“当前版本”；无法获得旧版本时必须说明限制，不可静默替换后声称是原结论的依据。

## 8. 统一 ContextBuilder 与预算

### 8.1 两条模式共享上下文准备

推荐主流程：

```text
用户问题
→ 校验会话、来源范围、历史关联设置
→ 读取当前摘要与近期消息
→ 理解问题、消解指代
→ 必要时检索并局部读取旧聊天
→ 完善检索计划与研究状态
→ Direct 检索 / ReAct 工具循环
→ 证据检查与引用定位
→ 按预算构建模型输入
→ 流式回答、保存完整轮次
→ 异步更新摘要和记忆索引
```

跨会话检索不一定要独立成一个新 Agent。先实现一个服务和少量工具即可，避免引入难以调试的多层 Agent 调度。

### 8.2 ContextBuilder 输出哪些内容

```text
可信系统规则与工具协议
本轮问题、回答模式、经过校验的文档范围
当前研究状态与结构化历史摘要
最近完整对话原文
本轮需要的历史聊天片段，带来源和时间
本轮已验证的文档证据，带稳定身份
当前轮合法的工具调用与结果
```

这是内容清单，不是要求把全部材料拼进 SystemMessage。摘要、历史、网页和原文都是可能不准确或含指令的外部内容，应作为有标签的数据提供；系统规则明确它们不能覆盖工具权限和回答约束。

用户显式的新要求优先于从旧聊天抽取的偏好。政策事实判断则依据问题要求的版本和原文，不能简单按“最近说过的优先”。

### 8.3 按模型窗口和任务预算控制输入

```text
可用输入上限 = 模型上下文窗口 - 预留输出 Token - 安全余量
本轮输入预算 = min(可用输入上限, 产品配置的成本/延迟预算)
```

计数必须覆盖提示词、工具 schema、历史、记忆、证据、当前调用链以及消息包装开销。使用相应模型的 Token 计数器；不支持精确计数时采用保守估计和余量，不把中英文字符按同一固定比例换算成精确 Token。

一个仅供初期配置的 16k 输入预算示例：

| 项目 | Token 上限示例 |
|---|---:|
| 系统规则、工具定义和当前问题 | 2,000 |
| 研究状态与旧历史摘要 | 1,000 |
| 最近原文 | 3,000 |
| 跨会话记忆片段 | 1,500 |
| 本轮政策证据 | 6,500 |
| 当前工具链与动态余量 | 2,000 |
| 合计 | 16,000 |

这些是设计示例，不是当前参数，也不是最优值。模型总窗口还要容纳单独预留的输出与安全余量；实际可以按任务动态分配。

当某一类超限时，优先去掉重复证据、低相关记忆和摘要已覆盖的旧原文，再缩短冗长材料。政策比较需要保留双方依据；当前工具调用协议、当前问题和关键用户约束不能被随意截掉。

最坏情况下，即使摘要任务失败，也应通过受控裁剪使请求有界，明确提示某个历史细节无法恢复。摘要成功不能成为不超窗口的唯一保障。

### 8.4 解决 Direct / ReAct 历史分歧

以用户可见的原始会话消息及其稳定序号作为对话内容依据。两种模式的新问题都从同一上下文服务读取摘要和近期完整轮次。

Checkpoint 继续负责 ReAct 当前执行与恢复。已有 checkpoint 与消息表之间使用 `last_synced_sequence` 一类游标同步必要的外部新轮次，使用稳定 message_id 去重。

不能直接把所有数据库历史和 checkpoint messages 再拼接一次，这会重复问题和答案；也不能在 resume 时把整个 messages 替换成数据库列表，这会丢失暂停中的工具执行状态。

## 9. 来源、权限与遗忘

这些要求直接服务于“历史召回正确且可解释”，不需要为每次只读召回增加确认弹窗。

- 第一版只检索当前用户自己的聊天。将来引入 workspace 时，再定义空间成员权限与共享范围。
- 检索前按用户/空间过滤，读取原始片段和原文时再次校验，不能只在前端隐藏其他人的结果。
- 记忆包含多个文档的混合摘要时，如其中某个来源已无权访问，不能仅删除 reference 后继续使用泄露内容。应跳过该混合片段，或基于仍可访问材料重建。
- 用户删除聊天或选择“不用于历史关联”后，派生摘要、向量和缓存也应失效；执行状态的保留/删除策略需要与现有 checkpoint 一并落实。
- 文档删除、重传或重切块时，标记相关来源定位失效，不能继续把旧助手答案作为替代原文。
- 用户可以打开被使用的历史出处、纠正记忆、排除某个片段。一次“不要这样写”不能自动删除之前的研究事实，但应更新适用的格式要求。
- 被新决定替代的旧决定保留时间关系，例如“曾用维度 A，后来改为维度 B”，避免简单覆盖导致无法回答历史回顾问题。

## 10. 在当前仓库如何分阶段落地

### 阶段一：先修当前对话

目标：不增加跨会话召回，也能稳定理解多轮追问。

1. 增加 QueryUnderstanding，先消解指代，再做元数据推断和文档检索。
2. 增加共享 ContextBuilder，让 Direct / ReAct 使用一致的上下文规则。
3. 统一消息序号与模式切换同步，区分完整轮次和失败消息。
4. 引入每次模型调用的 Token 预算，记录各组成部分的 Token。
5. 增加文档范围快照和稳定引用，避免把旧 `[1]` 当作新证据。

主要接入点：ChatTurnService、router、Direct generation、ReAct 模型调用前。

### 阶段二：结构化摘要和持续研究

1. 增加摘要版本、覆盖游标、研究状态。
2. 使用“较早历史摘要 + 最近完整轮次原文”。
3. 后台更新摘要；查询时保证游标之后原文仍可被读取。
4. 支持文档角色、比较维度、待办和来源集合版本。
5. 增加比较问题的分对象检索与覆盖检查。

先验收长聊天和文档切换，再扩大记忆范围。

### 阶段三：跨会话 episode 检索

1. 新增 MemoryService 与独立记忆索引，复用 PostgreSQL/pgvector。
2. 后台构建聊天摘要与片段向量。
3. 增加自动语义路由，以及搜索/局部读取工具。
4. 接入当前 ReAct 状态机与 Direct 编排，单独处理 conversation_recall。
5. 展示被使用的聊天出处、排除开关与来源不可用状态。
6. 支持人工指定旧聊天，作为自动检索不确定时的可靠入口。

### 阶段四：根据真实需求再扩展

长期用户偏好、团队研究空间、共享记忆、复杂任务图谱可以后续增加。第一版无需先做全部类型的语义/情景/流程记忆，也无需引入多 Agent。

### 10.1 建议的代码边界

以下是新增模块建议，不代表仓库当前已有：

```text
chat/application/context_service.py     统一读取会话摘要、近期消息与来源快照
chat/context/query_understanding.py     指代消解、任务分类、记忆意图
chat/context/builder.py                 构建模型输入与预算
chat/context/summary_service.py         结构化摘要及覆盖游标
chat/memory/service.py                  跨会话搜索和局部读取
chat/memory/indexer.py                  episode 构建、Embedding、版本发布
chat/memory/repository.py               持久记录与权限过滤
```

沿用现有 application 与 RAG 分工即可，不需要为此重构整个后端。

## 11. 怎样判断方案有效

不能只测试“检索到了相似聊天”。真正目标是帮助当前回答，同时避免错误记忆影响结论。

### 11.1 建议的评测场景

1. 当前聊天中的省略追问：“那它的申请条件呢？”
2. 长聊天超过近期窗口后，仍保留用户早先指定的比较维度。
3. 相同主题的新聊天，但用户从未表达延续意图，避免强行沿用旧决定。
4. 用户不说“历史记录”，只说“照上周那个框架”。
5. 用户提到“历史记录管理政策”，不能错误触发聊天回忆。
6. 两个相似研究具有冲突维度，系统不混合。
7. 同一研究追加第三份文档，并正确保留 A/B/C 的对象身份。
8. 从 A/B 切换为 C/D 后，旧文件事实不能被当成 C/D 的依据。
9. 历史助手答错、后来被用户纠正，召回时保留纠正关系。
10. 原文档删除、权限变化、重切块或版本更新。
11. 同一聊天 Direct → ReAct → Direct 切换。
12. 工具调用后 interrupt/resume，摘要更新不破坏恢复。
13. 用户删除聊天或关闭记忆后，召回结果立即遵循设置。
14. 刚完成的其他聊天尚未索引，显式指定时仍能读取。
15. 纯聊天回顾问题使用聊天出处，政策结论仍使用原文出处。

可以先人工构建几十条中英文场景作为起点，再依据真实错误补充。这个建议不代表当前仓库已有这套基线。

### 11.2 评测指标

| 环节 | 关注点 |
|---|---|
| 问题理解 | 指代消解正确率、是否擅自补入实体或条件 |
| 触发路由 | 应搜是否搜、不应搜是否误搜、显式关闭是否遵守 |
| 记忆召回 | episode Recall@K / MRR、用户原话定位准确性 |
| 最终回答 | 有益召回比例、错误记忆采用率、证据可追溯性 |
| 文档比较 | 比较对象和问题维度的证据覆盖 |
| 预算 | 输入 Token 分布、超限率、摘要和 Embedding 成本 |
| 体验 | 首个 Token 延迟、总延迟、澄清频率、来源可理解性 |
| 一致性 | 删除/权限/版本变更生效、模式切换和恢复正确性 |

每次请求记录 ContextSnapshot 的来源 ID、摘要版本、预算分配和实际使用的记忆 ID，无须把所有敏感原文复制进日志。

至少比较三组：当前实现；摘要 + Query Understanding；再加跨会话记忆。这样才能知道收益来自哪部分，避免把摘要带来的改善误归因于向量记忆。
