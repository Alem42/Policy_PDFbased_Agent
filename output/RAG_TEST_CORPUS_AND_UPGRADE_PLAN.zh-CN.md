## 1. 本次交付与建议顺序

已下载并校验 12 份官方 PDF，共 558 个物理页、20,551,228 字节，约 19.6 MiB。语料涵盖 AI 治理、隐私与数据治理、网络安全、气候能源、住房、生物安全，含中英文及美国、英国、中国、澳大利亚的文件。

语料、版本、哈希与复用信息在同级 rag-test-corpus-v1 目录。目录有 README、manifest.json、pdfs 和 download_corpus.py；脚本只校验或下载，不入库。此时完成的是“语料准备”，不是问答真值标注、准确率评测或内置测试集功能。

建议优先级：

1. 固定语料，建立真实问题及原文证据标注。
2. 修正文档身份、时间、对象与问题覆盖检查，低证据在后端确定性拦截。
3. 修正 chunk/模型输入预算，增加相邻段落读取和重复证据合并。
4. 试跑两个多语言本地模型组合，依据同一语料决定是否替换。
5. 上线一个小型跨 Chat 搜索工具，使用独立化问题加回答要点建立索引。

不建议先为技术名词建设 GraphRAG、多 Agent、用户画像或复杂长期记忆系统。

## 3. 当前用户问题究竟有没有被改写

目前没有 Direct/ReAct 共用的“问题改写服务”。

- Direct：主要直接使用 payload.question 构造 RetrievalRequest；history 用于回答，不会先自动形成统一的独立问题。
- ReAct：模型看到对话和工具定义后，自己生成检索工具的 query。提示词要求聚焦、拆分子主题和必要的不同表述，但这种改写是工具决策的一部分，不是固定执行一次的重写节点。
- metadata_filter_service.infer：以词项、地区标签、年份等规则推断过滤条件，不等于 LLM 改写。
- contextual_header：给文档 chunk 加背景，改的是入库检索表示，不是用户问题。
- 推荐追问生成器中的 standalone 要求，针对生成的新建议问题，不代表用户每个输入都已经经过同样处理。

## 4. 已认可的跨 Chat 索引策略：独立化问题 + 回答要点

### 4.1 每个完整轮次保存什么

```text
qa_id / session_id / user_id
原始用户问题 original_question
补全指代后的完整问题 standalone_question
用户可见最终回答 answer_text
检索用回答要点 answer_key_points
document_ids、文档版本、citation_refs、源消息 ID
回答状态、evidence 状态、创建时间、修订关系
embedding_model_version / embedding / indexed_at
```

向量索引文本示例：

```text
研究问题：比较 NSW 与另一地区住房政策的政府资金机制。
讨论结果：本次确定比较资金来源、申请主体、监督机制三个维度。
用户约束：只采用所选政策原文；尚未完成监督机制比较。
```

此处是数据结构示例，不是对本次语料内容的事实陈述。

原始回答与来源必须保留。Embedding 是查找入口，不替代原文。多次工具调用产生的子查询不能直接代替本轮完整问题，否则索引会把“研究中的一个小步骤”误当成整个问答主题。

### 4.2 不强制增加一次总结模型调用

1. 短回答直接使用全文作为回答要点。
2. 长回答优先使用已有明确结论段/用户决定，给索引设置长度上限。
3. 无可靠结论段时，第一版可以先索引独立问题，并保留回答全文供命中后读取；不要把随机截断称为完整准确摘要。
4. 用户显式决定、修正和未解决问题优先保留；不把用户换话题视为认可助手结论。
5. 以后确实出现长答细节召回不足，再异步补摘要或按主题拆片段。

第一版不要求每轮更新“整个 Chat 的总体摘要”，也不要求为每条单独消息建向量。

### 4.3 何时索引

完整回答成功落库后异步索引；失败记 pending/failed，后续补做。以 qa_id + index_version 幂等更新。暂停等待澄清的轮次不提前标成完成。

低证据拒答可以保存为“曾问过但未解决”的历史事件，不能把拒答或模型猜测写成已验证政策知识。后续修正某个回答时保留 supersedes 关系，默认召回最新有效决定；用户问“当时怎么说”时再读取旧版本。

### 4.4 如何检索与触发

第一版只增加一个有边界的工具：

```text
search_chat_history(query)
→ 按当前 user_id 过滤
→ 检索少量相关 QA（向量，可选关键词融合）
→ 去重、重排、选择少量候选
→ 返回相关问答与附近上下文，以及聊天、时间、来源定位
```

可以先给 ReAct 一段明确工具描述：用户要求延续以前研究、回顾历史、当前聊天缺少必需的旧决定时调用。无需先建设独立路由 Agent，也不要求用户说固定口令。若实测经常漏调用，再增加单独语义判断。

默认只搜索本人聊天。手动指定旧 Chat 时直接按授权 ID 读取，不用先向量搜索。工具返回有 Token 上限，不把整个命中聊天自动全部展开。

命中不是必须选第一名：可先取 3 个候选；无相关结果则不用；多个研究决定冲突时澄清。

### 4.5 记忆与 evidence 的边界

- 问“上次我选了哪些维度”：原始聊天是相应事实的出处。
- 问“某政策允许什么”：历史只帮助定位文件，政策结论回查当前允许的原文。
- 旧聊天里的 `[1]` 不是当前引用；保存稳定来源身份，本轮重新编号。
- 历史文本不能修改本轮工具权限，也不能静默把未选文档加入 Document Analysis 范围。

Direct 若需要同等能力，可通过编排调用同一搜索服务；不用要求所有用户都走更贵的 ReAct 循环。

## 6. DeepSeek 多模态与项目模型上下文

### 6.1 DeepSeek 现在是否支持图片

支持。当前官方推荐名 `deepseek-flash` 对应 DeepSeek-V4.1-Flash-1017，可接收图片与文字。项目中的旧名 `deepseek-v4-flash` 仍被官方作为兼容名接受并转到最新 Flash。当前定价表单列的 `deepseek-v4-pro` 不支持 Vision，不能把 Flash 的能力自动归给 Pro。[官方 Vision](https://api-docs.deepseek.com/guides/vision/)、[模型表](https://api-docs.deepseek.com/quick_start/pricing/)。

这不代表现有 Chat 页面已经支持图片对话。当前 ChatRequest 的 question 是字符串；还需要扩展消息内容块和图片上传/引用。现有扫描 PDF OCR 主要是先转文字，与直接传图片给视觉模型是两条路径。

### 6.2 仓库预置模型对应的窗口

以下根据仓库预置名称核对官方资料，不声称已审计运行数据库里用户额外添加的所有自定义模型。

| deepseek-v4-pro | 1M |

DeepSeek 旧 deepseek-chat/reasoner 记录不应继续按早年的规格推断；应跟随当前推荐型号与实际账号支持情况。智谱官网另有较新的 GLM-5.3/Flash 系列，但它们不是当前仓库这组预置名称，不应混作“项目已接入”。

### 6.3 大约能装多少页

页数没有固定换算率。此次语料英文非稀疏页面 cl100k_base 中位数约 516 Token；版式、表格、分词器会改变结果。可以先按每页 500–800 Token 粗算，并为系统提示、历史和输出合计预留 20%：

| 总窗口 | 按该假设可用于文档的约略页数 |
|---|---:|
| 128K | 128–205 页 |
| 200K | 200–320 页 |
| 1M | 1000–1600 页 |

这是规划推算，不是保证。密集双栏、中文分词、表格、图片和 OCR 输出会不同。最大输出也是单独的约束，不能把“最大输入窗口”与“最大输出”同时无条件叠加。

本组 12 份文件约 25.2 万 Token，只能说明长窗口模型在纯文本量级上可能容纳它们；不能证明把全部内容放进去一定比检索准确。项目自身还存在 context 字符上限和检索候选限制，不会因为换了 1M 模型就自动传入全部 PDF。

## 7. RTX 5070 Ti 16 GB 的本地模型建议

### 7.1 首先试的组合

**均衡首选试跑：Qwen3-Embedding-0.6B + Qwen3-Reranker-0.6B。**

**成熟对照：BGE-M3 + bge-reranker-v2-m3。**

前者适合建立多语言、小体积基线；后者适合对照传统编码器检索及精排。两者都比默认英文小模型更值得在中英文政策语料上验证。最终“更适合”应由本次语料的 Recall、困难负例误放行率与延迟决定，不依据厂商榜单直接宣布赢家。

| 模型 | 能力/窗口 | BF16/FP16 权重数量级推算 | 选择理由 |
|---|---|---:|---|
| Qwen3-Embedding-0.6B | 多语言，32K，最高 1024 维 | 约 1.2 GB | 第一轮的速度与效果平衡 |
| Qwen3-Embedding-4B | 多语言，32K，最高 2560 维 | 约 8 GB | 有验证收益时升级，控制 batch 和长度 |
| BGE-M3 | 多语言，8192，1024 维 | 约 1 GB 量级 | 同时提供 dense/sparse/multi-vector 能力，但第一版只用 dense 也可 |
| Qwen3-Reranker-0.6B | 多语言、指令型精排，32K | 约 1.2 GB | 与 Qwen Embedding 配套试跑 |
| bge-reranker-v2-m3 | 多语言 cross-encoder | 约 1 GB 量级 | 成熟的精排对照 |

权重推算不是实测总显存。激活、padding、batch、长输入及 CUDA 工作区会增加占用。0.6B 组合可以先给每个服务留数 GB 余量；4B Embedding 在 16 GB 上有希望运行，但不能据此承诺长输入和大 batch，也不能假设两个 4B 模型同时常驻还能余量充足。8B FP16 权重已约 16 GB，不是这张卡的首选。

来源：[Qwen Embedding 0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)、[4B](https://huggingface.co/Qwen/Qwen3-Embedding-4B)、[Qwen Reranker](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)、[BGE-M3](https://huggingface.co/BAAI/bge-m3)、[BGE reranker v2](https://huggingface.co/BAAI/bge-reranker-v2-m3)。

### 7.2 不是只改模型名称

当前 LocalFastembedProvider 使用 fastembed/ONNX，并没有在这里显式配置 CUDA provider。不能据此认定 5070 Ti 已被利用。

Qwen 模型需要合适的 Transformers/SentenceTransformers 或服务端 adapter，正确执行模型要求的 pooling、instruction 和精排模板。不能把 Qwen 名字直接塞进现有 fastembed 调用，就假定接口语义与分数一致。

5070 Ti 属于 Blackwell，安装推理环境时要选择支持相应架构的 PyTorch/CUDA 组合。[PyTorch Blackwell 支持说明](https://pytorch.org/blog/pytorch-2-7/)。此处是环境建议，本次没有执行安装或 GPU 速度测试。

切换模型后，必须重新计算对应文档向量并单独校准阈值；不同模型、维度、归一化或精排分数不得混用。Qwen 的 MRL 可以选择较小输出维度以降低存储，但这不意味着任意模型向量都可以随意截断。

### 7.3 “即调用即安装、用完卸载”怎样落实

拆成四件事：依赖安装一次；权重首次下载并缓存磁盘；请求到来时加载到显存；结束/空闲后释放显存。不要每次请求下载权重或卸载 Python 包。

推荐一个独立 GPU worker 管理模型：

```text
第一次调用 → 下载缺失权重 → 加载指定模型 → 推理
并发调用 → 引用计数/队列，共用一次加载
任务结束 → 释放输入、输出和模型引用
空闲约 60–120 秒 → 释放模型，或退出 worker
```

如果严格要求每次任务完成后显存全部交还，使用独立进程、完成后退出最容易保证边界；代价是每次冷加载。仅调用 torch.cuda.empty_cache() 不会释放仍被引用的模型，也不能当作完整卸载保证。并发存在时不能在其他请求还运行时卸载模型。

当前代码用 lru_cache 缓存 fastembed 和 reranker，没有上述自动释放生命周期。因此需要新增适配和管理，当前还没有实现。多 FastAPI worker 不应各自加载一份大模型；16 GB 预算应按整个 GPU 服务计算。Azure 部署也不会自动拥有本机 GPU，若继续在云端运行后端，本地模型需通过可达的推理服务调用。

## 8. 余弦相似度与其他向量用法

余弦相似度可用于语义召回、相似聊天发现、近重复内容候选、聚类和推荐，但它衡量的是模型表示下的相近程度，不是“这句话被证据证明”的程度。否定句、相近数字、不同年份或同主题不同国家仍可能非常接近。

更换距离公式通常不是当前最大收益点。单位归一化向量下，余弦、内积和欧氏距离的排序存在对应关系；应优先改进候选、粒度和证据验证。

| 机制 | 能解决什么 | 本项目优先级 |
|---|---|---|
| 相邻 chunk 合并、重叠去重 | 少把同一段的几个副本当成多份独立证据 | 高，改动小 |
| 按文档/地区/问题维度分组召回 | 防止某一文档占满 Top-K | 高 |
| MMR 多样性选择 | 相关候选里减少重复、提高材料覆盖 | 中；不得牺牲必须覆盖的比较对象 |
| 小块检索、大块读取 | 准确定位后读取邻近条件和例外 | 高 |
| 一个文档多个表示 | 标题/章节摘要找文档，原文 chunk 找证据 | 中，先做简单章节表示 |
| learned sparse / multi-vector / ColBERT | 更细的词级匹配、交互 | 中低；索引、存储和实现成本增加 |
| HyDE | 生成假想答案帮助召回 | 暂缓；虚构内容只能作查询，绝不能作 evidence |
| late chunking | 利用长文本编码上下文后再形成片段表示 | 暂缓；需要兼容模型与准确 token/片段映射 |

BGE-M3 支持 dense、sparse 和 multi-vector 不表示本项目换模型后会自动启用三种索引；每种都需要相应检索与融合实现。

## 9. Chunk 大小与 overlap

### 9.1 当前是什么

代码默认 `max_tokens=480`、`overlap=120`，按段落聚合，超长段落尝试句子切分，再回退字符切分。overlap 优先携带尾部段落，必要时携带尾句，并非每个 chunk 都恰好重复 120 Token。

入库时 chunk_budget 可配置；overlap 仍使用 chunker 默认值，并被限制为最多 max_tokens 的一半。标题/条款结构边界还没有完整实现，`section_title` 当前为 None。

[Chunker](E:/Study/UNSW/COMP9900/Demo1.2/capstone-project-26t2-9900-w11c-bread/backend/app/modules/documents/chunker.py:13)、[入库处理](E:/Study/UNSW/COMP9900/Demo1.2/capstone-project-26t2-9900-w11c-bread/backend/app/modules/documents/service/pipeline.py:90)。

### 9.2 overlap 为什么存在

政策里的主体、适用条件、例外与结论可能跨越切块边界。例如前一段规定一般规则，后一段以“但下列情况除外”开头；没有重叠或邻近读取时，检索到一段可能失去必要上下文。

重叠过大也有代价：增加向量数、入库成本、重复候选和重复上下文。理想固定窗口下，480/120 的重复系数约为 480/(480-120)=1.33，相比不重叠多处理约三分之一文本；实际段落算法会有偏差。

120 没有理论最优性。目前应视为默认启发式，而非经过本语料校准的最优结果。

### 9.3 当前尤其要修的预算问题

默认本地 BGE-small 的单段长度为 512。当前流程先切正文，再将 LLM 背景句放到 Embedding 输入前：

```text
Embedding 输入 = contextual_header + 原文 chunk
```

480 Token 的 chunk 加上背景句及模型特殊 Token 可能超限，而 chunker 没有预先扣除这些开销。模型截断时，chunk 原文末尾可能没有真正参与向量计算。Reranker 也要计算问题 + 段落 + 模板的组合预算。

应该校验最终实际输入，而不只校验原文 chunk 长度；模型长度不同也不能统一使用 8000 作为所有模型安全上限。

另一个小问题是中文句号后通常没有空格；当前句界正则要求标点后有空白，对这类中文长段落可能退回字符切分。可把中文标点边界单独处理。

### 9.4 建议起点

- 继续使用 512 长度旧模型时：先试正文约 350–400 Token，overlap 约 40–64，为背景和模板留空间。
- 改用长输入模型后：先试 512/64，再比较 768/96；不因为支持 32K 就直接生成 8K/32K 巨型 chunk。
- 尽量按章节、条款、自然段和表格行组保留边界；不同政策条款不要为了凑长度随意混合。
- 命中 chunk 后，按需要读取同章节前后相邻块，再重新检查实际支撑的条件与例外。扩展后的文本本身要做证据定位，不能凭邻接关系视为自动可信。
- 原文、页码和精确 quote 保持可追溯，标题/摘要只帮助检索。

用固定问题集比较 480/120、384/48，以及长模型下的 512/64、768/96。更换模型与更换分块是两个变量，尽量分别做对照。指标除 Recall/MRR 外，还要看正确引用跨度、重复率和遗漏例外的情况。

## 10. RAG 可选路线：没有一条路线包办所有需求

| 路线 | 适合什么 | 代价与局限 | 本项目建议 |
|---|---|---|---|
| 单路向量 RAG | 简单语义问答 | 名称/数字/地区容易混淆 | 不应倒退为仅此一种 |
| Hybrid + Reranker | 专有名词与语义同时重要 | 仍需覆盖和证据验证 | 已有，应做实测 |
| 结构化/父子块 RAG | 章条结构、条件和例外 | 需保留结构与来源映射 | 优先增加轻量版本 |
| Contextual Retrieval | chunk 脱离文档后难理解 | 入库成本、生成背景可能不准确 | 已有简化实现，先修预算与可追溯性 |
| Query decomposition / multi-query | 多对象、多维度问题 | 更多检索、去重与整体覆盖管理 | 有上限地增加 |
| Corrective / adaptive retrieval | 第一次检索不可靠时修正 | 容易无界重试，可能扩大错误范围 | 最多一次修正/补读；Analysis 不擅自联网 |
| Agentic RAG | 多步研究与工具协同 | 成本、稳定性、状态与策略复杂度 | 已有 ReAct，不必再堆多 Agent |
| GraphRAG / 图谱 | 跨库关系、全局主题总结 | 建图、实体消歧、更新与来源回链成本较高 | 暂不优先；图上关系仍需原文依据 |
| 长上下文直接阅读 | 文档少、总量可控 | 成本、延迟、定位与无答案判定仍存在 | 可作为评测对照，不替代证据约束 |
| 多模态/版面 RAG | 扫描、图表、复杂表格 | 解析、图片定位与验证更复杂 | 先定位真实解析失败再投入 |

上述是可组合的路线，不是“必须升级到某个流行框架”的阶梯。Self-RAG 原论文涉及专门训练的反思标记，简单加一个反思 prompt 不能宣称完整复现；CRAG 也不等于任何一次重试。可以采用其中的设计思想，但面试中应说明实际实现范围。

参考：[Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)、[Self-RAG](https://arxiv.org/abs/2310.11511)、[CRAG](https://arxiv.org/abs/2401.15884)、[GraphRAG](https://arxiv.org/abs/2404.16130)。

## 11. 最贴合客户要求的小改动：以证据契约约束回答

客户要求是 evidence 不足必须 block。最有价值的完善，是把 sufficient 从“有相似片段”推进为“必要问题有可定位的支撑”。

推荐流水线：

```text
原问题 → 对象/版本/必要子问题
→ Hybrid 检索 + 精排
→ 来源身份与问题覆盖检查
→ 生成带证据引用的草稿
→ 校验引用与关键结论是否被原文支持
→ 通过：发布答案；未通过/未知：block
```

### 11.1 先做确定性保护

1. **来源身份**：国家、发布机构、政策名称/编号、版本与本轮允许来源一致。不能只检查词汇在很多段落中分别出现。
2. **证据原文**：引用 ID 必须来自本轮检索集；quote 可在对应原文定位；页码和版本有映射。
3. **数字与条件**：金额、年份、比例、主体、否定/例外不能仅靠向量相似度通过。
4. **降级行为**：严格模式下，本次配置要求的验证器失败或没有结果，状态应为 unknown/block，而不是无标记沿用弱页面回退或失败开放。
5. **证据不是数量票决**：重叠 chunk 和同一原始来源的副本不能算相互独立印证。

### 11.2 增加一份很小的 coverage 表

例如比较 A/B 在资金与监督上的要求：

```json
{
  "requirements": [
    {"id": "A-funding", "status": "supported", "evidence_ids": ["e1"]},
    {"id": "B-funding", "status": "supported", "evidence_ids": ["e2"]},
    {"id": "A-oversight", "status": "supported", "evidence_ids": ["e3"]},
    {"id": "B-oversight", "status": "missing", "evidence_ids": []}
  ]
}
```

全部必要项有支持才允许完整比较。按照客户当前“低证据 block”的要求，缺一项默认不生成完整政策答案，说明缺口；如果以后允许部分回答，应作为明确的产品策略，而不是模型擅自决定。

检查必须针对原问题。ReAct 改写一个子查询后拿到 sufficient=true，不应直接让整个原始问题通过。

### 11.3 一次可解释的 support 检查

对少量候选或草稿关键结论，使用一次结构化判定：supported / contradicted / insufficient / unknown，必须返回引用 ID 和实际支持片段。服务端验证这些 ID/quote，而不是读取一个模型自报的“0.95 置信度”。

可以由便宜 API 模型或合适的 entailment 模型完成；是否同一模型、不同模型、是否增加成本，需要在困难负例上实测。相同生成模型自评可能重复同一种错误，不能宣称有绝对保证。

对弱结果最多做一次聚焦重检索/相邻段落补读；仍不足则停止。Document Analysis 不能因为想找够证据就自动跳到全库或网页。

### 11.4 SSE 的必要变化

如果先流出未经验证的正文，再检查失败，就已经违反“低证据内容不能输出”的体验要求。

严格模式建议先显示检索/校验进度，后端缓冲草稿；检查通过再发布正文，失败只发布 block 结果。这会增加首段正文等待时间，但不需要重构整个 Agent。仅在生成前 gate 通过、生成后不检查的方案更快，但对最终生成结论的保证更弱，应向客户区分。

无论验证发生在哪里，都不能承诺数学意义上的零幻觉。可以承诺明确的拦截策略、可审计理由，以及在已标注测试集上测得的误放行/误拦截结果。

### 11.5 小机制与投入估计

以下为熟悉仓库的一名开发者的初版工程量粗估，非交付承诺，不包含充分标注、硬件调试和生产验证。

| 改动 | 初版量级 | 收益 |
|---|---|---|
| 最终输入长度校验、背景预算、中文句界 | 约 1–2 天 | 防隐性截断，边界更完整 |
| 重叠去重、同章节邻块补读 | 约 1–3 天 | 条件/例外更完整 |
| 文档身份与 scope 检查 | 约 1–2 天 | 少引用错政策、错地区 |
| 必要子问题覆盖表 + 单次 support 检查 | 约 2–4 天 | 从主题相关推进到问题支撑 |
| 严格模式草稿缓冲与发布门槛 | 约 1–3 天 | 避免错误正文先流出 |
| 跨 Chat QA 索引与一个搜索工具 | 约数天 | 恢复先前研究，无需复杂记忆系统 |
| 校准与真实测试标注 | 持续工作 | 决定上述机制实际是否有效 |

小改动不等于无需评测。应优先报告 unsupported-answer rate、false-block rate、必要项覆盖、原文定位正确率，再报告 Recall/MRR、Token 与延迟。

## 12. 如何在面试中准确描述演进

尚未实现时，说“计划增加来源身份与问题覆盖检查”，不能说成已上线。

完成并经过测量后，可以描述为：

> 在现有混合检索和 ReAct 编排基础上，将证据判断分成相关性、问题覆盖和结论支撑三层；保留原文定位，严格模式在校验前缓冲答案，对缺失或未知证据执行确定性拦截。使用固定版本的跨领域中英文政策语料，分别评估召回、误放行与误拦截。

这比罗列 GraphRAG 等名字更能说明工程判断；其中最后的效果数字必须来自后续真实评测。
